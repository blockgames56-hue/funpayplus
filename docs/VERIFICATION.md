Backend-тесты используют временные SQLite-базы и mock HTTP-ответы. Проверены защита от повторной покупки при таймауте/перезапуске, запись состояния до отправки, частичное выполнение SMM, сохранение получателя и снимка услуги, ручная сверка без повторной отправки, последовательные платежи TON, уникальность SteamID, выдача/карантин/смена пароля аренды, доступ к Guard, сохранение ручного отключения лота и подтверждение тикета redirect-ответом. Дополнительно проверены журналы с пагинацией и поиском, исключение секретов, независимое сохранение модулей, сохранение шифротекста Steam при изменении Discord, редактирование/пауза поставщика, сохранение ключа LZT и cookie Roblox до остальных настроек, продление аренды после перезапуска, повторная проверка срока перед сменой пароля и применение текста покупателю. Тесты ранее существующих модулей и протокола FunPay входят в общий прогон.

Браузерная проверка тоже использует mock API. Скриншоты и сценарии находятся в `.verification/ui-browser/`; они не являются результатом работы с живыми заказами.

## Не подтверждено

- Реальные подключения FunPay, IMAP, LZT, SMM, BuySteamPoints, Fragment/TON, Steam и Telegram. Запросы покупки, отправка тикетов, изменения паролей и сообщений реальным покупателям не выполнялись.
- Установщик Tauri и frozen Python-sidecar: Rust toolchain отсутствует. Конфигурация упаковки обновлена, но `.exe` не пересобран.
- Python 3.12, macOS/Linux и PostgreSQL в этом прогоне.
- Нагрузка с 50 реальными лотами, задержки внешних API и FPS на компьютере пользователя. Разделение загрузки и ограничение параллелизма подтверждены кодом и локальными сценариями; это не нагрузочный benchmark.

## Повторный запуск Windows — 15.11.2026

`deploy/start.ps1` проверяет существующий backend до установки зависимостей, сборки и миграций. Если локальный API принадлежит FunPay Plus и отвечает по ключу текущего хранилища, повторный запуск открывает работающий экземпляр. Параметр `-NoBrowser` используется для автоматической проверки без открытия окна. Именованный mutex исключает два одновременных процесса установки/запуска.

`backend/launcher.py` резервирует сокет до миграций и обработчиков ASGI startup. При конфликте второй экземпляр завершается до запуска фоновых заданий. Проверка готовности не следует редиректам и не передаёт ключ сервису с чужой схемой API.

Проверено: 10 тестов `backend/tests/test_launcher.py`; два одновременных вызова Windows PowerShell с неизменным PID рабочего сервера; настоящий холодный запуск на отдельном порту с чистой тестовой базой и `WORKERS_ENABLED=false`, миграция до 0011 и отказ второго экземпляра до ASGI startup (`.verification/check-startup.py`). Рабочий сервер на 8765 не останавливался.
