## 4. Фактическое состояние, которое нельзя потерять

Стек: React 19, TypeScript, Vite, Tauri 2; FastAPI, SQLAlchemy, Alembic, SQLite, Python backend; FunPayAPI==1.1.0 в воспроизводимом окружении. Есть .venv и отдельная .venv-core, локальный Rust в .toolchains, MSVC Build Tools. Рабочий backend уже Python.

Основной путь: FunPayAPI Account/Runner → сериализованный executor аккаунта → accounts.ingest → SQLite IncomingEvent → event_pipeline → reply_engine → message_service → accounts.send → подтверждённый ответ FunPay. Каждый аккаунт имеет один последовательный executor для синхронного SDK, чтобы не блокировать async loop и не гонять его объекты параллельно.

Уже реализовано и проверено преимущественно офлайн:

- IncomingEvent сохраняется атомарно с ChatMessage; дедупликация по account/chat/server message ID; PROCESSING восстанавливается, FAILED повторяется вручную.
- MessageSend фиксирует исходящую попытку до сети. SENT только после подтверждённого server message ID; UNKNOWN не повторяется автоматически. Повтор ключа с другим payload отклоняется.
- Команды: точный префикс, exact, aliases, аргументы, регистр, приоритет, cooldown. Старый respond делегирует единому reply engine.
- Автоответчик: базовые приветствия/keywords, scope, blacklist, dry-run. Безопасный шаблонизатор без eval.
- Inbox: чтение чатов, история, ручная отправка, UI-блокировка двойного клика и сохранение текста при ошибке.
- Диагностика workers/очередей, ограничение частоты, backoff+jitter, graceful shutdown.
- Windows DPAPI current-user защищает master key; ключи аккаунтов в БД зашифрованы. Не ротируй ключи и не меняй шифрование без проверенного плана экспорта/восстановления.
- Заказы через FunPayAPI get_sells/get_order, ответы продавца на отзывы через send_review с проверкой и read-back, адресное поднятие через raise_lots и dry-run. Это не означает живую проверку этих мутаций.
- Чтение обычных лотов через get_user().get_lots(); неизвестный остаток — NULL, без выдуманного нуля. Изменение существующего лота — Account.save_lot с сохранением unchecked/специальных полей и read-back; dry-run не отправляет POST. Создание/копирование/удаление и комиссия ещё в legacy adapter.
- Inventory ledger: резерв и списание ключа атомарны, один резерв на заказ, ключ в резерве зашифрован, после сбоя uncertain без слепого повтора. Ручная сверка confirm_sent/release и глобальная проверка дубликатов между пулами и несвободными резервами. Миграции до 0019 проверены на пустой БД и копии backup, а не применены вручную к рабочей БД.
- Коммерческие маршруты, фоновые задачи и навигация старых плагинов отключены. Архивные файлы и некоторые shared imports всё ещё на диске.
- Tauri MSI и NSIS EXE, standalone core и onefile sidecar собраны. Sidecar и standalone прошли packaged smoke; release exe однажды показал dashboard с подключённым Python backend на пустом хранилище.

## 5. Что осталось: приоритет P0 — полный путь события и надёжность

1. Полный сквозной сценарий нового входящего: реальное или контролируемое входящее → Runner NEW_MESSAGE → нормализация → атомарный IncomingEvent/ChatMessage → WebSocket/UI Inbox → одна команда/одно правило → один подтверждённый исходящий ответ → журналы. На живом аккаунте автоматический ответ допускается только после отдельного согласования конкретного сценария; уже разрешённое одиночное тестовое сообщение не даёт разрешения на второй POST.
2. Проверь, что initial events не запускают ответ, own messages не отвечают самим себе, повтор event ID и тот же server message ID не создают дубль. Проверь restart до/после commit и после сетевого POST.
3. Runner при изменении чата использует пакетную историю. Проверь реальный путь события с актуальной разметкой и тесты на system/image/пустые/неожиданные сообщения, изменение в нескольких чатах, 50-chat limit. Не принимай успешное чтение истории за доказательство обработки NEW_MESSAGE.
4. Долговечный cursor/last-message state после перезапуска: отсутствие пропусков и ответов на старое. Если SDK не даёт надёжной удалённой пагинации, спроектируй ограниченную сверку по server ID. Документируй пределы, не обещай exactly-once сетевой доставки.
5. Удалённая история: пагинация, даты, timezone и неизвестные timestamp, медленные/пустые чаты, изображения и вложения. В Message SDK дата не гарантирована; не подставляй текущее время как дату старого сообщения.
6. Уточни сетевые ошибки: auth-expired, timeout до/после POST, 4xx/5xx, разрыв при shutdown, изменившаяся разметка, неожиданный ответ. Публичный API должен возвращать понятные безопасные коды и correlation_id; UNKNOWN должен иметь UI-путь ручной сверки, а не кнопку автоматического повтора.
7. Проверь reconnect и shutdown: один worker на аккаунт, пауза при отключении, сохранение состояния, отсутствие background-запросов после выхода. Не включай все автоматизации рабочего аккаунта для проверки.

Критерий P0: новая команда, сохранённая в UI, переживает перезапуск; новое входящее в тестовом чате отображается; при включённом целевом правиле формируется ровно один ответ; повтор события/перезапуск не отправляет второй; неподтверждённое исходящее имеет видимый UNKNOWN без повтора.

- Не выполнять возвраты, отзывы или изменения денег просто ради теста.

Автовыдача:

- На временной БД проверить несколько конкурентных заказов, один и тот же заказ после рестарта, пустой пул, дубликат ключа между пулами, резерв уже выданного/неопределённого заказа, отмену, потерю соединения после POST, недоступный исходный пул, confirm_sent/release и повторную сверку.
- Проверить сохранение зашифрованного резерва и заметки, отсутствие товара/секрета в diagnostics, логах и frontend-ошибках; одноразовость ключа при любой ошибке.
- Browser E2E для ручной сверки уже есть на отдельной БД, но полный сценарий от нового заказа до выдачи и после рестарта ещё нужен. Живая выдача требует отдельного согласованного заказа; не отправляй товар по существующим заказам.
- Разграничить один процесс SQLite и будущий распределённый worker/VPS. Не объявлять distributed ledger реализованным без атомарного межпроцессного механизма.

Лоты:

- Проверить редактор существующего лота по разным категориям и disabled/unchecked полям, read-back после save, dry-run без POST, отказ при расхождении как UNKNOWN. Никакой случайной публикации во время QA.
- Создание, копирование, удаление, расчёт комиссии ещё используют legacy adapters. Для каждого решить: переносить на достоверный метод FunPayAPI, сохранять проверенный адаптер с явным ограничением или убрать недействующее действие из UI с понятным объяснением. Не выдумывать SDK методы.
- Восстановление/деактивация лотов при отсутствии товара: тесты состояния, dry-run, повтор после сбоя, принадлежность аккаунту и категории, ограничения FunPay.
- Автоподнятие: серверный cooldown, расписание, группа/подкатегория, dry-run без POST, повтор события, собственность лота. Реальное поднятие только для согласованной категории/лота.

## 8. Что осталось: UI, плагины, упаковка и безопасность

UI: пройти все активные вкладки и каждую видимую кнопку на desktop и узком окне: обзор, аккаунты, входящие, команды/автоответчик, заказы/финансы, blacklist, лоты, автовыдача, прокси, настройки, логи/диагностика. Проверить loading, empty, success, error, offline, reconnecting, pending, disabled; перезагрузку окна, keyboard navigation, сохранение фильтров/черновиков, отсутствие фиктивных success. Сравнить ключевые экраны с прежним интерфейсом; проект не должен превращаться в простую админку.

Плагины: коммерческие маршруты и jobs отключены, но архивный код/shared imports остались. Составить import/dependency graph; отделить общие функции ядра; убрать активную загрузку произвольного кода и неиспользуемые runtime-зависимости без потери данных. Не возвращать старый магазин, платные интеграции, Steam/Roblox/TON/аренду/поставщиков в scope ядра. Не трогать локальные Cardinal/Pulse. Сохрани резервную копию и журнал решений, прежде чем физически удалять файлы.

Упаковка: MSI/NSIS уже собраны, но сами установщики не запускали в чистом Windows-профиле. Проверить установку, запуск, миграцию старой БД на копии, повторный запуск, shutdown, обновление поверх старой версии, uninstall без потери пользовательских данных, отсутствие второго backend, разрыв sidecar, долгий путь и кириллицу в имени пользователя. Для Linux/macOS или VPS только отдельные требования и тестовая среда; не заявлять их готовыми по Windows-сборке.

Секреты: DPAPI защищает текущую Windows-учётную запись, перенос на другого пользователя/компьютер требует отдельного экспорта. Не печатать golden_key, master key, token, чужие сообщения, товарные ключи и cookies. Проверять редактирование/удаление аккаунта, ротацию ключа, corrupted blob и backup/restore на копии. Не менять рабочее шифрование или БД без обратимого плана.

## 11. Команды воспроизведения

Запускай из C:\Users\User\Desktop\FunPay Plus\FunPay Plus, если не указано иное. Перед тестами выставляй отдельный STORAGE_DIR и WORKERS_ENABLED=false там, где приложение могло бы подключиться к рабочему аккаунту. Не запускай широкий старый test suite на рабочей БД.

npm run build
npm run desktop:build
.venv-core\Scripts\python.exe deploy/build-core.py

Для целевой Python-регрессии из каталога backend:

API-тесты могут требовать отдельного процесса: исторический test_api меняет env после импорта app.config и загрязнял смешанный запуск. Проверь это, прежде чем считать полный suite красным или зелёным. Актуальную схему API можно читать из локального /openapi.json после безопасного запуска. Из-за PyInstaller сборка sidecar может занять несколько минут; дождись окончания и выполни packaged smoke именно итогового бинарника.

Проверь миграции до head=0019 на пустой БД и копии backup: integrity_check, foreign_key_check, row counts и значения важных записей. Рабочую БД не мигрируй вручную для эксперимента. Не удаляй backup и старые настройки.

## 12. Жёсткие правила

- Не печатай, не цитируй и не переноси ранее предоставленный golden_key в промпты, скрипты, тесты, логи, issues и публичные артефакты.
- Не повторяй уже отправленное тестовое сообщение. Ранее полученное разрешение на один POST исчерпано.
- Не делай массовые сообщения, живую выдачу, отзывы, возвраты, удаление/редактирование/публикацию лотов и поднятие без согласования конкретного контролируемого объекта и ожидаемого эффекта. Пока готовь код, mock E2E, dry-run и изолированные UI-сценарии.
- Не обходи CAPTCHA, rate limits, защиту сайта, лицензии Pulse и ограничения стороннего API.
- Не запускай два backend на одной БД и не используй рабочую БД как тестовую.
- Не делай автоматический повтор UNKNOWN после возможного POST, даже если SDK выбросил исключение при разборе ответа.
- Не вводи второй набор команд/автоответов в старой plugin системе.
- Не удаляй архивные файлы или пользовательские настройки без проверенной карты зависимостей, backup и плана восстановления.
- Не обещай функциональную или визуальную эквивалентность без сценариев и доказательств.

## 13. Ожидаемый отчёт и критерий завершения

После каждого среза обновляй docs/IMPLEMENTATION_STATUS.md, docs/BACKEND_API.md и при необходимости карты функций; добавляй/обновляй SHA256 в docs/RECONSTRUCTION_CHANGES.json. Для отчёта нужны: что изменено и зачем; файлы; миграции; точные команды и результаты тестов; packaged/browser/live evidence; ограничения; риски; следующий шаг. Скриншоты только из реального UI после запуска, без секретов.

Итоговые статусы формулируй строго: «реализовано и проверено», «реализовано только офлайн», «частично», «не реализовано», «невозможно через текущий SDK». Начинай с анализа нового входящего события через Runner и durable cursor. Затем двигайся по P0 и P1, сохраняя уже работающие данные, интерфейс и сборки.
