# Проверка VPS, FunPayAPI и ошибок — 22.11.2026

## Подключение к VPS

Проверен полный клиентский сценарий на отдельном тестовом сервере с пустой базой: выбор VPS, проверка ключа, вход, запросы API, WebSocket, перезагрузка интерфейса, выход и повторный экран входа. Проверка выполнена в браузере с разными origin, затем в собранном Windows-приложении Tauri/WebView2 с настоящим IPC и CSP. Использовались отдельный профиль WebView2 и отдельная папка данных; рабочий магазин не изменялся.

Найдены и исправлены:

| Проблема | Исправление |
|---|---|
| Desktop всегда запускал локальный backend, включая режим VPS | Backend запускается по запросу только в локальном режиме. При выборе VPS с первого запуска локальная база и бизнес-воркеры не стартуют. Это проверено на настоящем `.exe`. |
| Переход с локального режима мог оставлять вторую автоматизацию | Перед сохранением VPS-подключения клиент запрашивает остановку локальных задач и завершает свой sidecar. Остановка не скрывает лоты на FunPay. Endpoint доступен только с loopback и требует ключ. |
| Любой HTTP 200 считался успешным подключением | Проверяются JSON, `ok`, тип базы, ключ и отсутствие редиректа. HTML reverse proxy отклоняется. |
| Неверный адрес, лишний `/api`, пробелы в ключе | Адрес нормализуется, `/api` удаляется; логин/пароль в URL, query, fragment и путь раздела отклоняются. Ключ очищается от внешних пробелов. |
| Недоступный сервер оставлял экран ожидания | Проверка сервера и начальная проверка сессии ограничены десятью секундами. |
| Enter в форме подключения отправлял внешнюю форму входа | Enter выполняет проверку и подключение к выбранному серверу. |
| Выход сохранял Bearer-ключ и позволял автоматически войти после reload | Сохранённый ключ удаляется при выходе. Проверено в браузере и native-клиенте. |
| CSP блокировала HTTP/WS через SSH-туннель на другом порту | Разрешены HTTP/HTTPS и WS/WSS соединения; ключ и Origin по-прежнему проверяются сервером. |
| В VPS-режиме показывалась постоянная метка LOCAL | Метка зависит от выбранного сервера; убрано неверное утверждение о локальном хранении данных. |
| Перенос под root требовал установленный sudo | SSH-скрипт выполняет команды напрямую под root, иначе использует sudo. |
| Второй каталог мог переиспользовать имя Compose-проекта и чужие тома | Перед запуском проверяется владелец существующего Compose-проекта. Другая установка не заменяется. |
| Установка с доменом могла сообщить об успехе до готовности HTTPS | После запуска проверяются публичный HTTPS, сертификат и авторизованный `/api/health`. Ошибка не выдаётся за успешное развёртывание. |

Обе Compose-конфигурации проверены настоящим Docker Compose CLI 5.8.0 (`config --quiet`). Docker Engine в этой среде отсутствует: Linux-образы, PostgreSQL, SSH-перенос на внешний VPS, публичный DNS, сертификат Caddy и перезагрузка реального VPS здесь не проверялись. Адрес VPS и GitHub-репозитория пока не предоставлены.

## Сверка с документацией FunPayAPI

Проект использует **неофициальную библиотеку FunPayAPI 1.1.0**, а не официальный публичный API FunPay. Проверены [описание и версия пакета](https://pypi.org/project/FunPayAPI/1.1.0/), [Account](https://funpayapi.readthedocs.io/ru/latest/account.html) и [Runner](https://funpayapi.readthedocs.io/ru/latest/runner.html), а также исходники установленной версии.

| Контракт | Результат |
|---|---|
| Инициализация `Account.get(update_phpsessid=True)` | Выполняется до работы с аккаунтом. Обновление сессии запрашивается через 40 минут, в пределах описанного интервала 40–60 минут. |
| Runner и события | Используется SDK Runner; синхронные обращения выполняются в отдельном сериализованном executor для каждого аккаунта. Исторические сообщения отделены от подтверждённых новых событий. |
| Сообщения и изображения | Проверяются фактический ID, отправитель, текст/изображение в ответе. Подтверждение не подменяется оптимистическим локальным успехом. |
| Поднятие лотов | Используются ID игры и список выбранных подкатегорий, обрабатывается серверное время ожидания. |
| Формы и сохранение | Сохраняются поля категории и состояния переключателей. После сохранения выполняется сверка. HTML-формы текущего сайта обрабатываются отдельно от старого JSON-парсера SDK. |

Дополнительно исправлены две ошибки транспорта:

1. `golden_seal` и PHPSESSID теперь передаются из SDK-сессии также в оставшиеся запросы расчёта цен, создания и копирования лотов. Раньше эти запросы могли использовать неполную сессию.
2. HTTP-ошибка SDK больше не превращается в общий тип до обработки повторов: безопасное чтение формы действительно повторяется при временных 429/5xx. Неизменяемые ошибки не повторяются. Редирект на вход определяется отдельно, внешние редиректы не выполняются автоматически.

Документация библиотеки описывает её интерфейсы и не гарантирует неизменность HTML сайта FunPay. Поэтому парсеры дополнительно проверены на сохранённых/синтетических примерах актуальной разметки. В этом прогоне сообщения клиентам, покупки, возвраты и реальные изменения лотов не выполнялись.

## Общая проверка проекта

**398 уникальных Python-проверок прошли** с учётом повторного прогона исправленных тестов и новых сценариев. Полный первоначальный прогон запускал каждый тестовый файл в отдельном процессе и временном хранилище. Один сбой относился к изоляции теста: новые обработчики плагинов обращались к другой базе. Исправлена подстановка общей тестовой сессии; все 16 проверок очереди событий затем прошли без изменения ожидаемого поведения.

Дополнительно прошли:

- Ruff для backend и deploy, проверка Python/JSON, синтаксис Bash и PowerShell.
- TypeScript и production-сборка Vite.
- `cargo check --release`, сборка Windows MSI/NSIS и запуск упакованного backend.
- Проверки адреса сервера, токена, неправильного JSON/HTML, HTTP 401/403/500, timeout и redirect policy.
- API/CORS preflight для Windows/macOS origin Tauri, проверка ключа, запрет постороннего origin, остановка локальных задач и отключение фоновых сервисов при `WORKERS_ENABLED=false`.
- Native-подключение к тестовому серверу, WebSocket, reload и logout; отсутствие запуска локального backend в VPS-режиме.
- Перенос SQLite, DPAPI-ключа и почтовых паролей; миграция копии старой базы; отказ повторного импорта; защита другого Compose-проекта.

Локальные протоколы: `.verification/full-audit-final.json`, `.verification/vps-final-protocol.log`, `.verification/vps-deploy-final.log`, `.verification/vps-core-pipeline.log`, `.verification/vps-audit-desktop.log`. Промежуточный неуспешный прогон сохранён отдельно для сравнения. Эти файлы и тестовые базы не включаются в GitHub-архив.

Это проверка перечисленных сценариев и найденных ошибок, а не доказательство отсутствия любых ошибок во всех внешних сервисах и сочетаниях настроек.
