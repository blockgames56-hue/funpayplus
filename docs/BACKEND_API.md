# Backend API: текущий вертикальный срез

API сохраняет существующие пути frontend, а не добавляет второй несовместимый контракт. Авторизация: существующий Bearer/session + origin checks. Backend слушает localhost; single ASGI process. Актуальная схема `/openapi.json`.

| Метод / путь | Действие |
|---|---|
| GET /api/health | Существующая проверка БД/сервиса |
| GET, POST /api/accounts | Список / добавление аккаунта |
| GET /api/chats | Чаты из SQLite |
| GET /api/chats/{id}/messages | Локальная история |
| POST /api/chats/{id}/refresh | Загрузить историю через FunPayAPI |
| POST /api/chats/{id}/messages | `{text, idempotency_key?}`; ключ обязателен для безопасного повтора клиентом |
| GET /api/workspaces/responder | Настройки, аккаунты, журнал ответов |
| PUT /api/workspaces/responder | Сохранить валидированные команды и правила; `dry_run` блокирует внешние отправки очереди |
| GET /api/automation/status | Состояния workers, last_poll, агрегаты журнала, unknown sends, последние события |
| POST /api/automation/events/{id}/retry | Только FAILED: повтор обработки, а не неизвестной отправки |
| POST /api/lots/bulk | Для `action:"raise"` поддержан `dry_run:true`: проверка категории без поднятия и изменения расписания |
| GET /api/automation/deliveries | Последние 100 резервирований: order_id/rule_id/state/даты; без ключей и текста выдачи |
| POST /api/automation/deliveries/{id}/resolve | `{action:"confirm_sent"|"release",confirmed:true,note:"..."}`; только uncertain, заметка 10–1000 символов |
| PUT /api/lots/{id}?dry_run=true | Проверка полей существующего лота; возвращает имена изменённых полей, не сохраняет лот |

Успешная текстовая отправка: `{ok:true, delivery_status:"SENT", message_id:...}`. До сетевого вызова в БД пишется UNKNOWN. Повтор того же key/text/chat возвращает подтверждённый SENT без второго запроса; другой payload с тем же ключом отклоняется. UNKNOWN не повторяется автоматически.

Правила: существующие `id, triggers[], reply, match, cooldown, enabled`; добавлены `case_sensitive, allow_arguments, priority`. Префикс — настройка workspace. Команда с полным префиксом в triggers поддерживается. Contains для команд нормализован до безопасного совпадения; свободный contains сохранён для keyword rules. Дополнительные необязательные `account_cooldown` и `buyer_cooldown` в секундах (0–86400) ограничивают то же правило во всех чатах аккаунта и у одного покупателя внутри аккаунта. Отсутствующие поля равны 0 для совместимости сохранённых правил.

WebSocket сохраняет channels `accounts,chats,orders,logs,...`; изменения чатов инвалидируют существующие frontend queries. Новый именованный event protocol из master prompt пока не введён, чтобы не ломать frontend.

Ошибки используют единый контракт: `{code, message, details?, correlation_id}` плюс legacy-поле `detail` для существующих вызовов. Код запроса доступен в заголовке `X-Correlation-ID` на всех ответах, включая 500. Коды: `unauthorized`, `rate_limited`, `not_found`, `conflict`, `validation_failed`, `invalid_request`, `bad_request`, `payload_too_large`, `forbidden`, `method_not_allowed`, `http_error`; FunPay-ошибки — 502 с `funpay_auth_expired`, `funpay_challenge_required`, `remote_unconfirmed` (не 401: истечение сессии FunPay не должно разлогинивать приложение); необработанные ошибки — 500 `internal` с безопасным сообщением и записью в лог только имени класса исключения и correlation_id. Тексты сообщений безопасны: внутренности исключений, пулы ключей и payload FunPay не попадают в ответы. `validation_failed` сохраняет прежний список `detail` (loc/msg/type) без input/context.

Dry-run поднятия возвращает отдельные `dry_run:true, raised:false, ok:true`: `ok` означает успешную проверку, не поднятие. Для других bulk-действий `dry_run:true` отклоняется с 422 до обработки лотов. Обычное поднятие сохраняет прежний контракт. В UI добавлена кнопка «Проверить поднятие», выделение лотов после проверки сохраняется.

Заказы теперь читаются через FunPayAPI `get_sells` (до трёх страниц за синхронизацию, защита от повторного cursor) и `get_order`. Неизвестная валюта отклоняется, сумма преобразуется через Decimal. Ответ продавца публикуется через `send_review` только после проверки владельца, закрытого заказа и существующего отзыва без ответа; результат сверяется повторным `get_order`. Чтение лотов использует `get_user().get_lots()`; неизвестный остаток возвращается как `amount:null`. Валютные предложения исключены из редактора обычных лотов. Изменение лотов пока использует прежний adapter.

Резервирование выдачи: `reserved → sent | uncertain`. Списание ключа из пула, зашифрованный резерв и `Order.delivery_state=sending` сохраняются одной транзакцией перед отправкой. Уникальный order_id запрещает второй резерв даже при ручном сбросе состояния заказа. При запуске workers незавершённые reserved/sending переводятся в uncertain без отправки и возврата ключа в пул. Старые завершённые выдачи не получают вымышленные записи задним числом. Поддерживается один backend process, как и в остальном ядре; распределённый inventory ledger не реализован.

Правила автоответчика допускают `active_days` (0 — понедельник, 6 — воскресенье) и необязательную пару `active_from`/`active_until` в формате `HH:MM`. Отсутствие полей сохраняет поведение старых правил: все дни и без ограничения времени. Расписание использует часовой пояс приложения; интервал с концом раньше начала считается ночным и относится к дню, в который начался.

Ручная сверка выполняется под delivery lock и не обращается в FunPay. confirm_sent отмечает заказ выданным. release атомарно возвращает ключ в исходный пул и переводит заказ в cancelled, резерв в released; повторная автовыдача этого заказа не запускается. Недоступный исходный пул, конфликт состояний или повторная сверка возвращают 409. Заметка оператора шифруется; она и товарный ключ отсутствуют в диагностическом ответе. UNKNOWN исходящая попытка становится MANUAL_CONFIRMED либо MANUAL_RELEASED, без выдуманного server message ID и возможности автоматического повтора.

Импорт пулов и выдача проверяют дубликаты между всеми пулами и неосвобождёнными резервами. Конфликт — 409 без раскрытия ключа. Существующие дубликаты не удаляются автоматически: их выдача блокируется. При удалении всей записи заказа каскадно удаляется связанный резерв; долгосрочный immutable audit за пределами жизненного цикла заказа пока не реализован.

Сохранение существующего лота использует Account.save_lot с подклассом LotFields, сохраняющим точные валидированные значения формы. Это обход ошибки нормализации unchecked active в SDK 1.1.0, а не обход прав FunPay. После POST get_lot_fields сверяет значения; расхождение — UNKNOWN, повторного POST нет. Создание/копирование/удаление лотов и расчёт комиссии пока используют прежние проверенные adapters. Dry-run проверяет форму, а не обещает успешный будущий POST.


### Durable Runner cursor (migration 0018)

Polling сохраняет на чат server message ID cursor, признак initial baseline и время последней сверки. Для существующих чатов migration использует максимальный уже сохранённый FunPay message ID; пустой чат получает baseline при первой успешной проверке. В Runner gateway история запрашивается пакетами до 10 чатов; до 10 давно не проверявшихся чатов ротируются в каждом цикле для ограниченной сверки. Только explicit Runner `NEW_MESSAGE` IDs или найденные выше установленного cursor IDs становятся кандидатами на automation. Initial/history messages только создают baseline/inbox, не ответ. Предел SDK: до 50 сообщений на чат (25 для отдельных типов); полной удалённой пагинации и гарантии восстановления длинного простоя нет. Повторные ID дедуплицируются SQLite; редактирование содержимого существующего message ID не диспетчеризуется повторно. Сетевой exactly-once не гарантирован.


### Единый контракт ошибок (реализовано 21 ноября 2026)

Все ошибки API — `{code, message, details?, correlation_id}` + legacy `detail`. `X-Correlation-ID` добавляется middleware и дублируется в теле каждого ответа, включая успешные. UNKNOWN исходящих по-прежнему не повторяется автоматически; ручная сверка deliveries сохранена как UI-путь. Фронтенд (`api.ts`) сначала читает новый контракт (включая `details`), затем legacy `detail`; correlation_id отображается в тексте ошибки (например, `... · ID 59be68158bf7`). Проверено: 9 интеграционных тестов контракта, 19 существующих API-тестов, HTTP-проверка на живом изолированном сервере (404/401/422/500) и повторение логики `api.ts` против реальных ответов; браузерный E2E-рендер в этой сессии не выполнялся (preview-автоматизация недоступна), TypeScript-сборка прошла.

### Scoped blacklist (migration 0019)

Запись blacklist имеет `scope`: `global`, `account` или `chat`. Старый запрос `{user_id, username?, reason?}` остаётся global для совместимости. Для account обязателен `account_id`; для chat обязателен `chat_id`, а `account_id` выводится из самого чата и не может противоречить ему. Одинаковый пользователь разрешён в разных областях, но точный дубликат области возвращает `409 conflict`. Активные пути core проверяют объединение global + текущий account + текущий chat и не дают account/chat-записи заблокировать другой аккаунт. Таблица UI показывает область; из Inbox создаётся chat-scoped запись. Импорт поддерживает global/account scope. Проверка выполняется до постановки ответа и непосредственно перед отправкой/выдачей. Архивные коммерческие plugin runtime отключены и остаются на прежней global-проверке; они не участвуют в active core.
